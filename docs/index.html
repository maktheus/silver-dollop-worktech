📚 JVM Classpath — Por que existe?

A JVM não compila tudo de uma vez como C/C++. Ela carrega classes sob demanda, em runtime. Para isso precisa saber onde procurá-las — essa lista de locais é o classpath.

🏭 C/C++ — Tudo resolve na compilação

O linker une todos os arquivos num único binário. Em runtime, não há busca — tudo já está lá.

# Um binário, tudo dentro
gcc main.c utils.c -o programa
./programa  # sem busca em runtime

☕ Java/Kotlin — Carregamento lazy

Cada classe é um arquivo separado. A JVM só carrega quando referenciada pela primeira vez.

# Cada classe = arquivo próprio
EnvironmentGuard.class
SecurityReport.class
DetectionSignal.class  ← carregado quando usado
🔍 Simulação: a JVM procura uma classe no classpath

💡 Por que isso importa para detecção de Xposed

Xposed injeta XposedBridge.jar no classpath de todo app no boot do Android. Se a classe XposedBridge é encontrada com Class.forName(), o Xposed está ativo — independente do nome do pacote ou de qualquer tentativa de ocultar.

try {
    Class.forName("de.robv.android.xposed.XposedBridge")
    // ↑ se chegou aqui = Xposed está no classpath → HIGH signal
} catch (_: ClassNotFoundException) {
    // ← esperado num dispositivo limpo
}

🎭 Façade Pattern

EnvironmentGuard esconde toda a complexidade. Do ponto de vista do chamador, é uma chamada só: generateReport(). Internamente orquestra 5 analyzers em paralelo, isola crashes e agrega resultados.

🔌 Strategy Pattern

Cada analyzer implementa EnvironmentAnalyzer. Adicionar um novo detector = criar uma nova classe. Sem tocar em nada existente. Isso é o "O" do SOLID (Open/Closed Principle).

🏭 Factory Method

Construtor private. Só o companion object instancia. Dois overloads: um para produção (lista hardcoded), outro para testes (lista injetada).

💉 Dependency Injection via Lambda

Sem framework (sem Hilt/Koin). Dependências como File.exists() e PackageManager são lambdas no construtor. Substituíveis em testes sem Robolectric.

detection/DetectionSignal.kt

DetectionSignal · SignalCategory · Severity

▼
data class imutável thread-safe equals/hashCode automáticos

O átomo de todo o sistema. Toda evidência detectada vira um DetectionSignal. Usa data class porque os testes fazem assertTrue(report.signals.contains(signal)) — isso exige equals por valor, não por referência.

Imutável por design: os 5 analyzers rodam em threads paralelas. Se DetectionSignal fosse mutável, precisaríamos de sincronização. Imutabilidade elimina o problema. 

enum class SignalCategory(val displayName: String) {
    EMULATOR("Emulator"),          // AVD, Genymotion, Nox
    CLONE_APP("Clone / Dual-Space"), // Parallel Space, VirtualApp
    VIRTUALIZATION("Hooking"),       // Frida, Xposed, Substrate
    ROOT("Root / Superuser"),        // Magisk, SuperSU
    SIGNATURE("Integrity"),           // APK repackageado
    SUSPICIOUS_PATH("Path"),          // arquivo de ferramenta
    SYSTEM_PROPERTY("Sys Property"),  // ro.debuggable, ro.secure
}
enum class Severity { LOW, MEDIUM, HIGH }

data class DetectionSignal(
    val category:    SignalCategory,
    val description: String,   // evidência concreta legível
    val severity:    Severity,
    val explanation: String = "", // contexto opcional para UI
)

detection/EnvironmentAnalyzer.kt

EnvironmentAnalyzer — fun interface (SAM)

▼
fun interface SAM conversion lambda instantiation

SAM = Single Abstract Method. Quando uma interface tem exatamente 1 método abstrato, o Kotlin permite instanciá-la com uma lambda. A palavra-chave fun antes de interface habilita isso. 

// ❌ interface normal — verboso nos testes:
val fake = object : EnvironmentAnalyzer {
    override fun analyze(ctx: Context): List<DetectionSignal> {
        return listOf(signal)
    }
}

// ✅ fun interface — uma linha em qualquer lugar:
fun interface EnvironmentAnalyzer {
    fun analyze(context: Context): List<DetectionSignal>
}

// No teste — instancia com lambda diretamente:
val goodAnalyzer = EnvironmentAnalyzer { listOf(goodSignal) }
val crashAnalyzer = EnvironmentAnalyzer { throw RuntimeException("crash") }
val emptyAnalyzer = EnvironmentAnalyzer { emptyList() }
detection/SecurityReport.kt

SecurityReport — data class com computed properties

▼

Computed property com get(): não existe backing field. O valor é recalculado toda vez que você acessa. Isso garante que nunca fica desatualizado.
Armadilha Kotlin 2.0: sumOf tem overloads para Int e Long. O bloco when impede inferência automática — precisa de .toInt() explícito. 

data class SecurityReport(val signals: List<DetectionSignal>) {

    // get() sem backing field = recalculado a cada acesso
    val isTampered: Boolean get() = signals.any { it.severity != Severity.LOW }

    val highSignals   get() = signals.filter { it.severity == Severity.HIGH }
    val mediumSignals  get() = signals.filter { it.severity == Severity.MEDIUM }
    val infoSignals    get() = signals.filter { it.severity == Severity.LOW }

    val riskScore: Int get() = signals.sumOf { signal ->
        when (signal.severity) {
            Severity.HIGH   -> 3
            Severity.MEDIUM -> 1
            Severity.LOW    -> 0
        }.toInt()  // .toInt() obrigatório no Kotlin 2.0 — sumOf ambíguo
    }
}
detection/EnvironmentGuard.kt

EnvironmentGuard — Façade + Factory + Orquestrador assíncrono

▼

Construtor private: ninguém cria diretamente. Só o companion object instancia, garantindo que sempre recebe context.applicationContext — evita leak de Activity.

Crash isolation: runCatching { }.getOrDefault(emptyList()) garante que se um analyzer lança exceção (ex: SecurityException ao ler /proc/net/tcp), os outros continuam rodando normalmente. 

class EnvironmentGuard private constructor(  // ← ninguém instancia direto
    private val context: Context,
    private val analyzers: List<EnvironmentAnalyzer>,
) {
    suspend fun generateReport(): SecurityReport = coroutineScope {
        val deferred = analyzers.map { analyzer ->
            async(Dispatchers.Default) {
                runCatching { analyzer.analyze(context) }  // crash isolado
                    .getOrDefault(emptyList())
            }
        }
        SecurityReport(deferred.awaitAll().flatten())
    }
    companion object {
        fun create(ctx: Context) = create(ctx,
            listOf(EmulatorAnalyzer(), CloneAnalyzer(), VirtualizationAnalyzer(),
                   SignatureAnalyzer(), RootDetector()))
        fun create(ctx: Context, analyzers: List<EnvironmentAnalyzer>) =
            EnvironmentGuard(ctx.applicationContext, analyzers)
    }
}

⚡ Coroutines — 5 Analyzers em Paralelo

Cada analyzer faz I/O bloqueante (/proc/cpuinfo, sockets TCP, leitura de arquivos). Rodá-los sequencialmente levaria 5× mais tempo. Com async/awaitAll rodam simultaneamente.

🔀 async { } — lança sem bloquear

Cria uma coroutine que executa no Dispatchers.Default (thread pool de CPU). Retorna um Deferred<T> — uma "promessa" de resultado futuro. O código continua sem esperar.

⏳ awaitAll() — espera todos

Bloqueia (suspende) até que todos os Deferred completem. Se um falhar, cancela os outros (mas usamos runCatching para evitar isso). Retorna List<List<DetectionSignal>>.

🛡️ runCatching { } — crash isolation

Envolve o analyze() em try/catch implícito. Se um analyzer lança exceção, o getOrDefault(emptyList()) retorna lista vazia. Os outros analyzers não são afetados.

📋 .flatten() — achata resultado

Transforma List<List<DetectionSignal>> em List<DetectionSignal>. O SecurityReport recebe uma lista plana única com todos os signals.

Emuladores — Farms de Fraude em Escala

HIGH
▼

🔴 O que o atacante faz

Roda 200+ emuladores AVD/Genymotion num servidor. Cria 10.000 contas falsas/dia. Simula localizações em qualquer lugar do mundo. Reset completo em segundos via snapshot.

🟢 Como detectamos — 4 camadas

Build.* properties + SystemProperties via reflection + arquivos QEMU em /dev + marcadores em /proc/cpuinfo. Um emulador raramente engana todas as 4.

// Camada 1: Build.FINGERPRINT
// Emulador AVD: "generic/sdk_gphone_x86/generic_x86:11/RSR1..."
// Dispositivo real: "google/flame/flame:12/SQ3A.220705.003.A1..."
val fp = Build.FINGERPRINT.lowercase()
if (fp.startsWith("generic") || fp.contains("emulator")) { /* HIGH signal */ }

// Camada 2: Build.HARDWARE
// goldfish = nome do hardware virtual do QEMU desde Android 1.0
// ranchu = hardware do QEMU 2+ (Android Studio atual)
if (Build.HARDWARE.lowercase() in setOf("goldfish", "ranchu", "vbox86")) { /* HIGH */ }

// Camada 3: arquivo exclusivo do QEMU
// Só existe no emulador, nunca num device real
if (File("/dev/socket/qemud").exists()) { /* HIGH signal */ }

// Camada 4: /proc/cpuinfo — CPU virtual do QEMU
val cpu = File("/proc/cpuinfo").readText()
if (cpu.contains("goldfish", ignoreCase = true)) { /* HIGH signal */ }

Root / Magisk — Controle Total do Dispositivo

HIGH
▼

Magisk (systemless root): em vez de modificar a partição /system (bloqueada pelo dm-verity), o Magisk monta um filesystem virtual via tmpfs sobre o /system. Do ponto de vista do app, o sistema parece intacto. Mas o binário su está disponível em caminhos específicos.

⚠️ O que root permite
  • Editar /etc/hosts (MITM de DNS)
  • Instalar CA customizado no sistema
  • Rodar frida-server
  • Ler banco de dados de outros apps
  • Remontar /system como writable
✅ Nossas 4 defesas
  • 9 paths de binário su
  • 12 root management apps
  • ro.debuggable, ro.secure
  • /system canWrite() check
// /system sempre read-only num device limpo
// se canWrite() = true → foi remontado com root
val writableProbe: (String) -> Boolean = { File(it).canWrite() }

// ro.debuggable=1: adb root funciona, sem senha
// ro.secure=0: sem enforcing de permissões Linux
// ro.build.type=eng: build de engenharia (vai para usuário final em fraude)
val clazz = Class.forName("android.os.SystemProperties")
val get = clazz.getMethod("get", String::class.java, String::class.java)
val debuggable = get.invoke(null, "ro.debuggable", "") as String
if (debuggable == "1") { /* HIGH signal */ }

Clone Apps / VirtualApp — Identidade Paralela

HIGH
▼

Apps como Parallel Space criam um "Android virtual" dentro do processo deles. Seu app roda como processo filho com UID diferente — pode nem saber que está num container.

👤 Usuário Primário
UIDs: 10.000 – 99.999
userId = myUid() / 100.000 = 0 ✓
dataDir: /data/data/com.app
👤👤 Usuário Clone
UIDs: 110.000 – 199.999
userId = myUid() / 100.000 = 1 ⚠️
dataDir: /data/user/10/com.app
// Android aloca UIDs em blocos de 100.000 por usuário
// Primário: 10.000–99.999  │  Usuário 1: 110.000–199.999
val userId = Process.myUid() / 100_000
if (userId != 0) { /* rodando em usuário secundário → CLONE */ }

// dataDir revelando o clone:
// Legítimo: /data/data/com.incognia.guardapp
// Clone:    /data/user/10/com.incognia.guardapp ← userId=10
val expected = listOf(
    "/data/data/${context.packageName}",
    "/data/user/0/${context.packageName}"
)
if (expected.none { dataDir.startsWith(it) }) { /* HIGH signal */ }

// /proc/self/maps denuncia a biblioteca nativa do clone:
// "com.lbe.parallel" ou "io.va" mapeado → Parallel Space ativo
File("/proc/self/maps").forEachLine { line ->
    if (line.contains("com.lbe.parallel", ignoreCase = true)) { /* HIGH */ }
}

🪝 Frida — Instrumentação Dinâmica

A ferramenta mais poderosa de análise de apps Android. Permite interceptar qualquer função em runtime sem modificar o APK.

Animação: fluxo Frida atacando o SDK

🔴 Como o Frida ataca

1. frida-server roda como root na porta 27042
2. Script JS via USB hookeia generateReport()
3. Substitui a implementação para retornar SecurityReport(emptyList())
4. O SDK acha que o dispositivo está limpo

🟢 Nossas 3 defesas

1. Socket probe: tenta conectar em 127.0.0.1:27042 com timeout de 150ms
2. /proc/net/tcp: procura porta em estado LISTEN
3. /proc/self/maps: detecta frida-agent.so mapeado

// Script Frida que burlaria SDK sem proteção:
Java.perform(() => {
  const Guard = Java.use('com.incognia.guardapp.detection.EnvironmentGuard');
  Guard.generateReport.implementation = async function() {
    return Java.use('SecurityReport').$new(Java.use('ArrayList').$new());
  }; // ← retorna sempre "limpo"
});

// Defesa 1: socket probe (executa ANTES do Frida hookar)
Socket().use { socket ->
    socket.connect(InetSocketAddress("127.0.0.1", 27042), 150)
    // conexão bem-sucedida = frida-server rodando → HIGH signal
}

// Defesa 3: /proc/self/maps — mesmo que a porta esteja bloqueada
// "7f8a3000-7f8b0000 r-xp 00000000 fd:01 1234  /data/local/tmp/frida-agent-64.so"
File("/proc/self/maps").forEachLine { line ->
    if (line.contains("frida", ignoreCase = true)) { /* HIGH signal */ }
}

🔌 /proc/net/tcp — Decodificando o Kernel

O parser mais técnico do projeto. Entender o formato evita falsos positivos que derrubam a confiabilidade do SDK. Bug real encontrado nessa sessão: 0x699A ≠ 27042.

🐛 Bug real corrigido — porta hex errada

O código original usava "699A" = 27034 decimal. A porta do Frida é 27042 = 0x69A2. O socket probe usava o valor correto; o parser de /proc/net/tcp estava silenciosamente procurando a porta errada. Os testes passavam porque testavam a lógica do parser, não a conversão numérica.

🔢 Decodificador interativo — clique nos bytes para entender o formato
local_address = 0100007F:69A2 — IP + Porta
IP (little-endian hex):
01 00 00 7F : Porta (big-endian hex):
69 A2
Resultado:
Clique num byte para decodificar…
IP = little-endian (bytes invertidos): 01 00 00 7F → inverte → 7F 00 00 01 → 127.0.0.1
Porta = big-endian (ordem normal): 69 A2 → 0x69A2 → 27042
Exemplo real de /proc/net/tcp — linha com Frida em LISTEN:
sllocal_addressrem_addressstinterpretação
0: 0100007F:69A2 00000000:0000 0A ⚠️ 127.0.0.1:27042 em LISTEN = Frida server!
1: 0200007F:C350 0100007F:69A2 01 ✓ ESTABLISHED — não é listen, ignorar
2: 00000000:0050 00000000:0000 0A Port 80 em LISTEN — outro serviço, ignorar 
// Por que parts[1] e parts[3] (não contains na linha toda)?
// → "69A2" pode aparecer no remote_address (parts[2]) em ESTABLISHED
// → comparar na linha toda geraria falsos positivos

internal fun parseTcpTable(lines: List<String>, sourcePath: String = ""): List<DetectionSignal> {
    val fridaPortHex = "69A2"  // 27042 = 0x69A2  ← BUG CORRIGIDO nessa sessão
    for (line in lines) {
        val parts = line.trim().split(" ").filter { it.isNotEmpty() }
        if (parts.size >= 4) {
            val localPort = parts[1].substringAfter(":")  // ← coluna LOCAL
            val state = parts[3]                           // ← coluna ESTADO
            if (localPort.equals(fridaPortHex, ignoreCase = true)
                && state.equals("0A", ignoreCase = true)) {
                // porta 27042 em LISTEN na interface LOCAL = Frida server
            }
        }
    }
}

🥷 Stealth — Ocultando Strings no APK

Um analista que tenta entender o SDK pela engenharia reversa não deve ver facilmente quais strings ele busca. O charArrayOf é a primeira camada de defesa.

🔍 Como funciona a extração de strings

Ferramentas como jadx, apktool e até o comando strings extraem literais de string da seção .rodata do DEX. Strings literais no código Kotlin ficam armazenadas estaticamente no APK — qualquer pessoa consegue ver.

Comparação: o que aparece numa extração de strings do APK
❌ String literal — aparece no APK:
val marker = "goldfish"  // → visível em: strings app.apk | grep goldfish
🔴 "goldfish" — ENCONTRADO por strings
🔴 "qemu" — ENCONTRADO
🔴 "genymotion" — ENCONTRADO
✅ charArrayOf — invisível no APK, reconstruído em runtime:
val goldfish = charArrayOf('g','o','l','d','f','i','s','h').concatToString()
// jadx vê: new char[]{'g','o','l','d','f','i','s','h'}
// strings vê: nada — não há string literal "goldfish" no DEX
✅ "goldfish" — NÃO encontrado por strings
⚙️ char[]{'g','o','l'...} — jadx vê chars, não string

🔒 R8 Full Mode (release)

O build de release usa R8 em modo completo: renomeia classes para a/b/c, remove código morto, faz inline de métodos. Dificulta engenharia reversa sem precisar escrever código extra.

🔑 Próximo nível (produção)

DexGuard (pago), criptografia de strings em runtime, anti-tamper via hash do próprio DEX, e JNI — lógica crítica em C/C++ que o Frida Java API não hookeia facilmente.

🔄 Fluxo Completo — Do Launch ao Servidor

8 passos do onCreate() até a decisão final. A decisão de bloquear fica no servidor — fora do alcance do Frida.

1

App inicia — MainActivity.onCreate()

lifecycleScope.launch {} garante que a coroutine é cancelada se a Activity morrer. Não bloqueia a Main thread.

2

EnvironmentGuard.create(this).generateReport()

Factory garante applicationContext. generateReport() é suspend — pode ser chamada de qualquer coroutine.

3

5 coroutines lançadas em paralelo com async{}

Cada analyzer recebe Dispatchers.Default — thread pool separado. I/O de /proc não bloqueia a UI thread.

4

runCatching isola falhas individuais

SecurityException ao ler /proc/net/tcp? O analyzer retorna emptyList(). Os outros 4 continuam normalmente.

5

awaitAll() — todos os 5 terminam

Retorna List<List<DetectionSignal>>. O mais lento determina o tempo total — por isso paralelismo importa.

6

flatten() → SecurityReport criado

isTampered = any { severity ≠ LOW }. riskScore = Σ(HIGH×3 + MEDIUM×1). Imutável por design.

7

runOnUiThread { renderReport() }

Volta para a Main thread para atualizar a UI. HIGH (vermelho) → MEDIUM (laranja) → LOW (azul).

8

riskScore enviado ao servidor Incognia

O SDK não bloqueia localmente. A decisão (permitir/negar login) fica no backend — onde o atacante não pode usar Frida para alterar a resposta.
